# 技术选型文档

## 1. 技术栈总览

| 层 | 选型 | 版本 | 选型理由 |
|---|---|---|---|
| 后端框架 | FastAPI | 最新稳定 | 异步、自动生成 API 文档、类型提示友好 |
| LLM | 智谱 GLM-4.5-Flash | - | 免费、已有 API Key、Anthropic 兼容协议 |
| Embedding | bge-small-zh (本地) | - | 免费离线、中文效果好、可观察 embedding 过程 |
| 向量库 | Chroma | 最新 | 纯 Python、零配置、RAG 流程暴露清晰、适合学习原理 |
| RAG 框架 | LangChain | 最新 | 生态成熟、文档丰富、Agent 化可无缝升级 |
| 文档处理 | python-docx + pymupdf | 最新 | docx 读写 + PDF 解析，已验证可行 |
| 配置管理 | pydantic-settings | 最新 | 类型安全配置、支持 .env |
| 数据校验 Hook | 自定义中间层 | - | 生成后自动校验实验定律 |

## 2. 为什么不用其他方案

### 2.1 向量库为什么选 Chroma 而非 Redis Stack
- Chroma 纯 Python，pip 即用，零服务运维
- 分块→embedding→存→检索的流程暴露最清楚，适合理解 RAG 原理
- Redis Stack 放到工程化阶段（v7）作为生产环境升级，届时复用已有 Redis 经验

### 2.2 Embedding 为什么用本地 bge 而非 API
- 完全免费、离线可跑
- 能亲眼看到 embedding 向量的计算过程，理解原理
- 学习阶段不需要高并发，本地性能足够

### 2.3 为什么第一版不用 Agent
- 规则编排可控、好调试，每步能验证中间结果
- 先跑通 RAG + LLM 生成，再上 Agent 时清楚每个工具怎么用
- 企业现状：大部分"Agent 应用"也是规则编排 + LLM 节点

### 2.4 为什么第一版不做前端
- 核心是验证 AI 生成链路，前端次要
- 开发者未学过前端，第一版加前端会分散精力
- 第三版再做前端正好练 Vue3

## 4. 接口设计草案

### 4.1 生成报告
```
POST /api/reports/generate
Content-Type: multipart/form-data

请求体:
  - experiment_content: str          # 实验内容文字
  - raw_data: str                    # 结构化数据 (JSON/CSV)
  - template: file (.docx)           # 报告模板
  - reference_reports: files (.pdf)  # 参考报告
  - requirements: str                # 生成要求

响应:
  200 OK
  {
    "code": 0,
    "data": {
      "docx_url": "/files/report_xxx.docx",
      "pdf_url": "/files/report_xxx.pdf",
      "sections": {
        "purpose": "...",
        "principle": "...",
        ...
      }
    },
    "msg": "success"
  }
```

### 4.2 检索参考（调试用）
```
GET /api/rag/search?q={query}&top_k={n}
响应: 检索到的参考片段列表
```

## 5. RAG 设计

### 5.1 文档处理流程
1. **解析**: pymupdf 读取参考报告 PDF，提取文本
2. **分块策略**: 按章节分块（目的/原理/内容/结果/讨论），每块带元数据（章节类型、实验名称）
3. **Embedding**: bge-small-zh 生成向量
4. **存储**: 存入 Chroma，元数据含章节类型，便于过滤检索
5. **检索**: 按"实验内容"关键词检索，优先返回同类型章节的片段

### 5.2 RAG 的三个作用
1. **内容参考**: 检索相似实验的各章节写法
2. **格式对齐**: 检索章节结构、表格格式、图题命名规范
3. **校验依据**: 检索实验定律原理，校验生成数据

## 6. LLM 生成设计

### 6.1 结构化输出
LLM 返回 JSON 格式，各章节作为独立字段：
```json
{
  "purpose": "实验目的...",
  "principle": "实验原理...",
  "procedure": "实验步骤...",
  "results_analysis": "结果分析...",
  "discussion": "实验讨论...",
  "summary": "实验小结..."
}
```

### 6.2 Prompt 结构
```
[系统角色] 你是一名电工电子实验报告撰写助手...
[参考资料] {RAG 检索结果}
[实验内容] {用户输入的实验内容}
[生成要求] {用户输入的要求}
[输出格式] 严格返回 JSON，包含以下字段...
```

## 7. 数据校验 Hook

生成后自动校验，不符合则标记或重新生成：
- KCL: ΣI = 0
- KVL: ΣU = 0
- 数据范围合理性检查
- 必要字段非空检查
