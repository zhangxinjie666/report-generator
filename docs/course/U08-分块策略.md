## 概念讲解

### 1. 分块：RAG 的地基，检索的最小单位

**一句话定义**：分块（Chunking）是把长文档切成若干独立小段（chunk）的预处理步骤，每块**单独向量化、单独被检索、单独进 prompt**——它是 RAG 检索的最小单位。

**例子**：一份 5 页的参考报告不切块会怎样？向量模型对"整份报告"只能给出一个向量，十几个主题被压成一团；切块后，"三、实验原理"是一个块、一个向量，查询"实验原理"才能精准命中它。

**项目中在哪**：`rag_engine.py` 的 `_chunk()` 方法。入库链路是 `解析 → 清洗 → 切块 → 向量化 → 入库`，检索链路召回的就是这些块。U6 你"看库"看到的每一条记录，就是一个块。

**为什么它是地基（本单元最重要的一段话）**：检索召回的是块 → 块主题混杂，向量方向就被几个主题"平均化"（U7 实验 3 的结论反过来用：向量量的是"意思的位置"，混合块的意思在几个主题之间漂移）→ 查询向量跟混合块的距离整体被拉大、排序被污染。链路每一环都会把失真放大：**Embedding 修复不了坏块，检索修复不了坏向量，生成修复不了坏检索**——所以 U6 那句"语料决定检索上限"现在可以升级为：**语料和切块决定检索质量的上限，后面的环节只能尽量逼近这个上限。**

### 2. 解剖现状：滑动窗口是怎么切歪的

`rag_engine.py` 当前方案：`chunk_size=350, overlap=60`，步长 step = 350 − 60 = 290：

```text
整页文本（清洗后连成一串，标题/目的/仪器/原理/图注…全在里面）
[────────────────────────── 900 字 ──────────────────────────]
块1 [0 ───── 350]
块2      [290 ───── 640]     ← 开头的 60 字和块1 尾巴重叠（overlap）
块3           [580 ───── 930]
       ↑ 切在哪只由数字决定——"三、实验原理"正好被拦腰切断？没人管。
```

**优点**：实现只要 10 行、块长均匀、永远不会超 token 上限。**缺点**：切分边界完全无视语义——U6 实验 1c 你亲眼见过作案现场：第 1 页切出的块里，"三、实验原理基尔霍夫定律……功率不可叠加"和标题、仪器混在一块。

**项目中在哪**：`_chunk()` 就是固定滑窗。它是**通用兜底方案**——对没有结构的纯散文（聊天记录、评论）合理；对实验报告这种**强结构文档**，是高射炮打蚊子还打歪了。

### 3. chunk_size 与 overlap 的权衡

**chunk_size（块长）**：

- **太大**：一块塞多个主题 → 向量方向平均化（本项目 350 字的教训）；同时低相关文本挤占 prompt 上下文，生成时注意力被稀释
- **太小**：语义不完整，检索回来的碎片 LLM 没法用来写正文；块数暴增，存储和检索开销上升
- **硬约束**：bge-small-zh 上限 **512 token**（中文约 1 字 ≈ 1 token），chunk_size 必须留余量——本项目 350，就是为了"超长章节二次切分"之后子块仍安全

**overlap（重叠）**：防止"关键句恰好跨边界，两块各剩半句"——半句话的向量两头不靠，谁也检索不准。代价：存储冗余；同一句话可能被两个块重复召回，占掉 top_k 的名额。

**关键认知（U6 诊断顺序的呼应）**：**"按什么边界切"比"切多长"更重要**。本项目的病根是无视结构（切法错），不是 350 这个数字（长度错）——所以 U8 的药方是换切法，不是调参数。

### 4. 三种主流切分策略

| 策略 | 怎么切 | 适用场景 | 代表实现 |
|---|---|---|---|
| 固定长度滑窗 | 按字符数硬切 + 重叠 | 无结构纯散文、快速原型 | `rag_engine._chunk()`（现状） |
| 递归字符切分 | 按 `\n\n` → `\n` → 句号 → 空格 逐级降级，尽量在自然边界断开 | 通用文档（不知道结构但通常有段落） | LangChain `RecursiveCharacterTextSplitter`（默认） |
| 结构感知切分 | 按文档自带的结构标记（Markdown 标题、HTML 标签、"一、二、三"章节）切 | 强结构文档：报告、手册、代码 | 本单元你要亲手写的 |

**认知扩展**：还有"语义切分"（按相邻句子向量的突变点找边界），属于进阶技巧，现在知道名字即可。

**选型口诀（面试可用）**：先问**文档有没有结构**——有结构就顺着结构切（结构是作者已经替你标好的语义边界），没有再退到递归/滑窗；切块的目标是**"为检索准备语义完整的最小单元"**。

### 5. 结构感知切分的设计要点（本单元要亲手写的）

实验报告是强结构文档：标题独立成行、"一、二、三"编号规整。四个设计要点：

1. **标题锚点**：用正则匹配"中文数字 + 顿号"开头的行（`一、实验目的`、`三、实验原理`），标题行就是天然的语义边界
2. **块自带语义信号**：切片从标题字符开始 → 每块开头就是"三、实验原理" → 向量方向被主题词主导。这正是 U6 实验 2 你手工"只摘原理段"检索表现好的原因——你当时做的事，本质就是把标题和正文重新绑回一个纯块
3. **免费的结构化 metadata**：每块顺手记录"所属章节"存进 Chroma 的 metadata → 将来可以按章节过滤检索（比如"只在实验原理章节里找"）。这是结构切分白送的红利，U9 会用到
4. **超长章节二次切分**：章节内部超过 chunk_size 就退化为滑窗——**工程上没有纯策略，只有组合策略**。子块保留标题做块首，语义信号不丢

**一条工程认知（来自 lab 脚本的设计）**：`rag_engine` 清洗时把整页拼成一串，**标题行的信息丢了**；lab 脚本的提取函数刻意**保留行结构**，因为标题识别靠"独立成行"。教训：**清洗策略要服务于切分策略**——数据管道的每一步都在为下游设计，改下游要回头看上游。

## 常见误区

1. **"块越细越好，检索更精准"**。错。小块召回准但语义残缺——检索是给 LLM 供料的，喂碎片写不出正文。粒度要匹配**下游谁在用**：检索只求"指得准"，生成需要"说得全"。
2. **"检索不准先调 chunk_size"**。错。按 U6 定的诊断顺序：先看块全文，分清是"切法错"还是"长度错"。本项目的病根是切法。
3. **"overlap 越大越保险"**。错。重叠过大 = 存储冗余 + 重复召回 + 相邻块相似度过高，top_k 名额被"同一句话的两个版本"占满，检索多样性反而下降。
4. **"按字符切 = 按 token 切"**。半错。中文粗略 1 字 ≈ 1 token，但混排英文、数字、标点时偏差会被放大；chunk_size 的上限必须按**模型 token 上限（512）**倒推，不能拍脑袋。
5. **"切分策略随便改，库里数据还在"**。错。块是入库的最小单位，改切分 = 全量重新切块 + 重建入库。别指望 upsert 救场：块 id 是"文件名-序号"，切法一变序号全变，旧块残留库里就是检索污染（呼应 U7：换 Embedding 模型同理，全量重建）。
